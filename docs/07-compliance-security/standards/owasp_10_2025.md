### 2. SECURE DEVELOPMENT LIFECYCLE (SDLC) & AI AGENT GUARDRAILS

AI Agent dan sistem pengembang otomatis wajib mematuhi aturan prinsip (_Guardrails_) saat menghasilkan atau meninjau kode sumber:

```
+-----------------------------------------------------------------------------------+
|                        AI AGENT SECURE CODING GUARDRAILS                          |
+-----------------------------------------------------------------------------------+
| 1. Never Hardcode Secrets     : Gunakan Environment Variables / Secrets Vault.     |
| 2. Parameterize All Queries   : Jangan gunakan String Concatenation untuk SQL.     |
| 3. Enforce Ownership Checks   : Validasi userId pemilik data pada setiap query.   |
| 4. Sanitize Output & Input    : Gunakan Context-Aware Escaping & Validation.      |
| 5. Fail Securely              : Tangkap exception dan kembalikan generic error.   |
| 6. Use Strong Cryptography    : Gunakan SHA-256/Argon2id, hindari MD5/SHA1/DES.   |
+-----------------------------------------------------------------------------------+
```

### A01:2025 - BROKEN ACCESS CONTROL

#### 1. Deskripsi & Overview

Broken Access Control terjadi ketika sistem gagal menegakkan batasan akses pengguna yang terdaftar. Pengguna yang tidak sah dapat mengakses, mengubah, atau menghapus data milik pengguna lain, atau mengeksekusi fungsi administratif tanpa hak istimewa yang sesuai.

#### 2. Skenario Kerentanan

- **Insecure Direct Object Reference (IDOR / BOLA):** Pengguna mengakses `GET /api/v1/orders/1001`. Pengguna mengganti ID menjadi `GET /api/v1/orders/1002` dan dapat melihat pesanan orang lain karena sistem tidak memeriksa kepemilikan data.
- **Missing Function Level Access Control:** Pengguna biasa dapat mengakses endpoint admin `POST /api/v1/admin/delete-user` hanya dengan mengetahui URL-nya.
- **CORS Misconfiguration:** Pengaturan CORS `Access-Control-Allow-Origin: *` dengan kredensial diaktifkan yang memungkinkan situs jahat mencuri data pengguna.

#### 3. Cara Pencegahan & Mitigasi Teknis

1. **Deny-by-Default:** Secara bawaan, tolak semua akses ke API/endpoint kecuali diizinkan secara eksplisit.
2. **Access Control Enforcement:** Selalu verifikasi hak akses di tingkat server pada _Service Layer_ atau _Domain Layer_, bukan hanya di UI.
3. **Record-Level Authorization Check:**
   ```python
   # Contoh Kode Aman (Python/FastAPI)
   @app.get("/api/v1/orders/{order_id}")
   def get_order(order_id: int, current_user: User = Depends(get_current_user)):
       order = db.query(Order).filter(Order.id == order_id).first()
       if not order:
           raise HTTPException(status_code=404, detail="Order not found")
       if order.user_id != current_user.id and current_user.role != "ADMIN":
           raise HTTPException(status_code=403, detail="Access denied")
       return order
   ```
4. **Disable Directory Browsing:** Matikan fitur _directory listing_ di web server (Nginx/Apache).

### A02:2025 - SECURITY MISCONFIGURATION

#### 1. Deskripsi & Overview

Security Misconfiguration mencakup kesalahan dalam konfigurasi server, framework, komponen cloud, atau database. Hal ini mencakup penggunaan pengaturan bawaan (_default settings_), fitur berbahaya yang tidak perlu diaktifkan, atau pesan kesalahan yang terlalu terperinci (_verbose error logs_).

#### 2. Skenario Kerentanan

- **Debug Mode Aktif di Produksi:** Kerangka kerja web (seperti Django/Laravel) dijalankan dengan `DEBUG=True`, menampilkan informasi rahasia, environment variables, dan _stack trace_ saat terjadi kesalahan.
- **Default Credentials:** Menggunakan password bawaan pabrik/admin pada database atau panel manajemen (misal: `admin/admin` atau `root/root`).
- **Unprotected Cloud Buckets:** Cloud Storage (AWS S3/GCS) dikonfigurasi dengan akses publik (_Public Read_) berisi data sensitif.

#### 3. Cara Pencegahan & Mitigasi Teknis

1. **Automated Hardening Process:** Gunakan skrip otomatisasi atau Infrastructure as Code (IaC seperti Terraform/Ansible) untuk menerapkan konfigurasi yang aman.
2. **Minimalist Footprint:** Hapus atau matikan fitur, modul, dan sampel kode yang tidak diperlukan.
3. **Secure Error Handling:** Konfigurasikan server untuk tidak pernah menampilkan _stack trace_ atau informasi internal ke pengguna akhir.
4. **Security Headers:** Terapkan header keamanan HTTP penting:
   - `Content-Security-Policy (CSP)`
   - `Strict-Transport-Security (HSTS)`
   - `X-Content-Type-Options: nosniff`
   - `X-Frame-Options: DENY`

### A03:2025 - SOFTWARE SUPPLY CHAIN FAILURES

#### 1. Deskripsi & Overview

Kategori ini berfokus pada risiko yang bersumber dari komponen pihak ketiga, pustaka open-source, dependensi perangkat lunak, serta saluran pipa CI/CD (_Continuous Integration / Continuous Deployment_). Serangan terjadi ketika peretas menyisipkan kode jahat ke dalam _dependency repository_ atau memanipulasi _build pipeline_.

#### 2. Skenario Kerentanan

- **Dependency Confusion / Typosquatting:** Mengunduh pustaka palsu dengan nama yang mirip dengan pustaka populer (misal: `reqeusts` alih-alih `requests`).
- **Compromised NPM/PyPI Package:** Pengembang menggunakan pustaka open-source terpercaya yang akun maintenernya diretas dan disisipi _backdoor/malware_.
- **Insecure CI/CD Pipeline:** Rahasia (_secrets_) CI/CD tidak dilindungi sehingga penyerang dapat menyuntikkan langkah _build_ palsu untuk mengubah artefak produksi.

#### 3. Cara Pencegahan & Mitigasi Teknis

1. **Software Bill of Materials (SBOM):** Buat dan kelola dokumen SBOM untuk melacak seluruh komponen, versi, dan asal-usul dependensi.
2. **Automated Dependency Scanning:** Integrasikan alat pemindai kerentanan dependensi (seperti Snyk, Dependabot, Trivy, atau OWASP Dependency-Check) dalam saluran CI/CD.
3. **Lock & Pin Dependencies:** Gunakan file _lockfile_ (`package-lock.json`, `poetry.lock`) dan _pin_ versi dependensi spesifik beserta _hash SHA-256_.
4. **Code Signing:** Tandatangani secara digital seluruh _commit_ Git dan artefak _build_ menggunakan kunci GPG/Cosign.

### A04:2025 - CRYPTOGRAPHIC FAILURES

#### 1. Deskripsi & Overview

Gagalan kriptografi sebelumnya dikenal sebagai _Sensitive Data Exposure_. Fokusnya adalah pada kegagalan terkait kriptografi yang sering mengarah pada terungkapnya data sensitif atau kompromi sistem (seperti data finansial, data pribadi, atau kata sandi).

#### 2. Skenario Kerentanan

- **Data Transmission in Cleartext:** Mengirimkan data login atau transaksi melalui protokol non-enkripsi seperti HTTP, FTP, atau TELNET.
- **Weak Password Hashing:** Menyimpan kata sandi menggunakan algoritma usang dan cepat seperti MD5, SHA-1, atau SHA-256 tanpa _salt_.
- **Hardcoded Secret Keys:** Menyimpan kunci enkripsi atau _private key_ langsung di dalam kode sumber aplikasi.

#### 3. Cara Pencegahan & Mitigasi Teknis

1. **Enkripsi Transit (In-Transit):** Wajibkan protokol TLS 1.3 untuk seluruh komunikasi jaringan. Gunakan HSTS (_HTTP Strict Transport Security_).
2. **Enkripsi Istirahat (At-Rest):** Enkripsi data sensitif di database menggunakan AES-256-GCM.
3. **Password Hashing Standar:** Gunakan algoritma _adaptive/key-stretching_ khusus kata sandi:
   - **Argon2id** (pilihan utama)
   - **Bcrypt**
   - **PBKDF2**
4. **Secrets Management:** Simpan kunci kriptografi dan _secret keys_ dalam sistem manajemen rahasia terpusat (_HashiCorp Vault_, _AWS Secrets Manager_).

### A05:2025 - INJECTION

#### 1. Deskripsi & Overview

Kerentanan Injection terjadi ketika data yang tidak terpercaya diselipkan ke dalam interpreter sebagai bagian dari perintah atau kueri. Data jahat tersebut memperdaya interpreter untuk mengeksekusi perintah tanpa izin atau mengakses data tanpa otorisasi.

#### 2. Skenario Kerentanan

- **SQL Injection (SQLi):** `SELECT * FROM users WHERE username = 'admin' OR '1'='1'--` mengeksekusi kueri yang selalu bernilai benar.
- **Command Injection:** Aplikasi menerima masukan nama file dari user dan menjalankan kueri sistem: `os.system("cat " + user_input)`.
- **Cross-Site Scripting (XSS):** Menyuntikkan skrip JavaScript jahat ke dalam komentar aplikasi yang dieksekusi di peramban pengguna lain.

#### 3. Cara Pencegahan & Mitigasi Teknis

1. **Parameterized Queries / Prepared Statements:**
   ```python
   # Contoh Kode Aman (Python/PostgreSQL)
   cursor.execute("SELECT * FROM users WHERE username = %s AND password_hash = %s", (username, password_hash))
   ```
2. **Gunakan ORM secara Aman:** Manfaatkan kerangka kerja ORM (SQLAlchemy, Prisma, Eloquent) dengan benar tanpa mencampur kueri mentah (_raw SQL_).
3. **Allowlist Input Validation:** Validasi semua masukan pengguna berdasarkan tipe data, panjang, dan pola regex yang diizinkan.
4. **Context-Aware Output Encoding:** Gunakan kerangka kerja UI modern (React, Vue, Svelte) yang secara otomatis melakukan _escaping_ XSS pada variabel yang ditampilkan.

### A06:2025 - INSECURE DESIGN

#### 1. Deskripsi & Overview

Insecure Design berfokus pada cacat pada tingkat desain dan arsitektur sistem. Berbeda dari kesalahan implementasi (bugs), kerentanan ini terjadi karena tidak dilakukannya evaluasi risiko, pola arsitektur yang salah, atau ketiadaan _threat modeling_ sebelum kode ditulis.

#### 2. Skenario Kerentanan

- **Cacat Logika Pemulihan Kata Sandi:** Fitur reset password hanya mengandalkan pertanyaan keamanan umum yang mudah ditebak.
- **Absensi Rate Limiting pada Logika Bisnis:** Sistem pembelian tiket tidak membatasi jumlah reservasi per menit, memungkinkan _bot script_ memborong seluruh tiket.
- **Eksploitasi Trust Assumptions:** Menganggap bahwa masukan dari microservice internal selalu aman tanpa perlu otentikasi/otorisasi tambahan.

#### 3. Cara Pencegahan & Mitigasi Teknis

1. **Threat Modeling:** Lakukan _Threat Modeling_ (seperti STRIDE) pada tahap awal perencanaan arsitektur fitur baru.
2. **Secure Design Patterns:** Terapkan pola arsitektur aman: _Zero Trust Architecture_, _Principle of Least Privilege_, dan _Segregation of Duties_.
3. **Business Logic Rate Limiting:** Batasi frekuensi panggilan API pada fungsi kritis (login, transaksi, kirim OTP, reset password) menggunakan Redis/API Gateway.
4. **Pencegahan Fraud & Abuse:** Buat alur kerja bisnis yang memperhitungkan potensi penyalahgunaan otomatis oleh bot.

### A07:2025 - AUTHENTICATION FAILURES

#### 1. Deskripsi & Overview

Gagal Otentikasi terjadi ketika aplikasi gagal memverifikasi identitas pengguna secara benar, sehingga memungkinkan penyerang meretas kata sandi, mengambil alih sesi, atau menyamar sebagai pengguna lain.

#### 2. Skenario Kerentanan

- **Credential Stuffing & Brute Force:** Aplikasi memungkinkan percobaan login berulang kali tanpa batas dari IP yang sama.
- **Permissive Password Policy:** Mengizinkan kata sandi lemah seperti `123456` atau kata sandi yang telah bocor dalam daftar kerentanan umum.
- **Insecure Session Tokens:** Token JWT dibuat menggunakan kunci rahasia yang lemah (`secret123`) atau tidak dikoreksi saat pengguna melakukan logout.

#### 3. Cara Pencegahan & Mitigasi Teknis

1. **Multi-Factor Authentication (MFA):** Wajibkan MFA (TOTP/WebAuthn/Passkey) terutama untuk akun administratif dan transaksi sensitif.
2. **NIST Password Guidelines:** Batasi kata sandi berdasarkan daftar _pwned passwords_, jangan membatasi penggunaan karakter unik/karakter khusus, dan izinkan penggunaan _password manager_.
3. **Rate Limiting & Lockout:** Terapkan _Exponential Backoff_ atau penundaan progresif setelah percobaan login yang gagal.
4. **Secure Cookie & Session Flags:**
   - Set flag cookie: `HttpOnly`, `Secure`, `SameSite=Strict`.
   - Lakukan regenerasi Session ID / JWT Token setelah login berhasil dan hancurkan token saat logout.

### A08:2025 - SOFTWARE OR DATA INTEGRITY FAILURES

#### 1. Deskripsi & Overview

Kerentanan ini berkaitan dengan asumsi bahwa perangkat lunak, pustaka, data, atau pembaruan yang diunduh/diterima dapat dipercaya tanpa memverifikasi integritasnya. Hal ini mencakup pula kerentanan _Insecure Deserialization_.

#### 2. Skenario Kerentanan

- **Insecure Deserialization:** Membaca objek ter-deserialisasi dari masukan pengguna yang tidak terpercaya (misal: `pickle.loads()` di Python atau `unserialize()` di PHP) yang mengeksekusi kode perintah jarak jauh (_Remote Code Execution / RCE_).
- **Unverified Auto-Update:** Perangkat lunak mengunduh pembaruan otomatis melalui saluran HTTP biasa tanpa memverifikasi _digital signature_ dari file _installer_.

#### 3. Cara Pencegahan & Mitigasi Teknis

1. **Digital Signature Verification:** Selalu verifikasi tanda tangan digital atau _hash checksum_ (SHA-256) pada file atau paket perangkat lunak sebelum dieksekusi.
2. **Aman dari Deserialization:** Hindari melakukan deserialisasi objek kompleks dari sumber luar. Gunakan format data terstruktur yang netral seperti JSON atau Protocol Buffers (protobuf).
3. **Signed JWT Claims:** Jika menggunakan token atau state terdistribusi, pastikan data ditandatangani secara kriptografis menggunakan algoritma _asymmetric_ (RS256/ES256).

### A09:2025 - SECURITY LOGGING AND ALERTING FAILURES

#### 1. Deskripsi & Overview

Ketiadaan atau ketidakcukupan pencatatan (_logging_), pemantauan (_monitoring_), dan peringatan (_alerting_) mencegah organisasi untuk mendeteksi serangan siber yang sedang berlangsung, memahami pola peretasan, dan merespons insiden secara cepat.

#### 2. Skenario Kerentanan

- **Auditable Events Unlogged:** Kegagalan otentikasi berulang, akses data sensitif, dan perubahan hak akses admin tidak dicatat dalam log.
- **Logs Stored Locally & Plaintext:** Log ditulis dalam file lokal server yang dapat dihapus oleh peretas jika server berhasil ditembus.
- **No Real-time Alerts:** Serangan _brute force_ atau _data exfiltration_ terjadi selama berhari-hari tanpa ada peringatan otomatis ke tim Security/DevOps.

#### 3. Cara Pencegahan & Mitigasi Teknis

1. **Log High-Value Events:** Catat seluruh aktivitas penting: Login/Logout, Kegagalan Otorisasi, Perubahan Data Sensitive, Modifikasi Hak Akses, dan Kegagalan Validasi Server.
2. **Centralized & Immutable Logging:** Kirim log secara _real-time_ ke server log terpusat (SIEM / ElasticStack / Datadog) yang dikonfigurasi _write-once-read-many_ (WORM).
3. **Structured Log Format:** Gunakan format log terstruktur (seperti JSON) yang mencakup: `timestamp` (UTC), `event_type`, `user_id`, `source_ip`, `status`, dan `trace_id`.
4. **Automated Alerting Thresholds:** Atur ambang batas peringatan otomatis (misal: > 50 kegagalan login dalam 1 menit) ke saluran komunikasi darurat (Slack/PagerDuty).

### A10:2025 - MISHANDLING OF EXCEPTIONS AND EXCEPTIONAL CONDITIONS

#### 1. Deskripsi & Overview

Kerentanan ini berkaitan dengan kegagalan sistem dalam menangani kondisi pengecualian (_exceptions_), kesalahan runtime (_errors_), atau kondisi batas (_edge cases_) secara aman. Penanganan kesalahan yang tidak tepat dapat menyebabkan sistem "gagal dalam keadaan terbuka" (_fail-open_), membocorkan data internal, atau menyebabkan kondisi pasca-kesalahan yang tidak konsisten (_inconsistent state_).

#### 2. Skenario Kerentanan

- **Fail-Open Exception:** Pada fungsi verifikasi pembayaran, jika panggilan API payment gateway mengalami _timeout_ atau melempar _exception_, sistem menganggap pembayaran telah berhasil secara otomatis.
- **Sensitive Data Leakage in Stack Trace:** Saat kueri database gagal, sistem mengembalikan seluruh pesan kesalahan database beserta tabel, kolom, dan variabel koneksi ke peramban pengguna.
- **Unreleased Resources / Leaks:** Ketika terjadi kesalahan pada alur pemrosesan file, file handler atau koneksi database tidak ditutup di blok `finally`, menyebabkan kehabisan sumber daya server (_Denial of Service_).

#### 3. Cara Pencegahan & Mitigasi Teknis

1. **Fail-Secure Defaults:** Pastikan bahwa setiap kali terjadi kondisi pengecualian (_exception_), sistem secara otomatis mengasumsikan kondisi paling aman (menolak transaksi, menolak akses, dan melakukan _rollback_).
2. **Global Exception Handler:** Terapkan penanganan _exception_ global di tingkat aplikasi untuk menangkap semua kesalahan yang tidak ditangani (_uncaught errors_) dan mengembalikan pesan respons generik:
   ```json
   {
     "status": 500,
     "error_code": "INTERNAL_SERVER_ERROR",
     "message": "Terjadi kesalahan pada sistem. Silakan hubungi dukungan teknis dengan ID Referensi: REFF-20260802-9912"
   }
   ```
3. **Use Try-Catch-Finally for Resource Cleanup:** Pastikan setiap sumber daya (koneksi database, socket, file descriptor) ditutup dalam blok `finally` atau menggunakan _context manager_ (`with` statement di Python / `using` di C#).
